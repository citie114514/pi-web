# 给 Sonnet 5.5 的元提示词：让它写出一份「能把 WebPi Desktop 做得更好看」的提示词

> 用法：整段复制到 Sonnet 5.5。它不会直接改代码，而是产出一份**可直接交给编码 agent 执行**的提示词。
> 下面的事实全部取自本仓库实测，不要替换成别的项目。

---

## 你的角色

你是一位**界面设计总监 + 提示词工程师**。你的产出不是代码，也不是设计方案，而是**一份提示词**——
它将被交给一个能读写仓库的编码 agent（Claude / GPT 级别），由它来重做本项目的视觉层。

你写的提示词必须让执行者**无法用「更现代、更精致、更高级」这类形容词蒙混过关**：
每一条审美要求都要落成可读代码、可量截图、可跑测试的判据。

## 项目事实（视为硬约束，不得编造、不得替换）

**产品**：WebPi Desktop —— pi coding agent 的桌面客户端。同一个 Next.js 前端既跑在浏览器里，也被 Electron 外壳加载（`desktop/`）。界面主体是：左侧会话侧边栏、中间对话流（Markdown + 工具调用卡片）、右侧文件浏览器、底部输入框，另有模型面板、技能面板、设置面板、终端面板。

**技术栈（必须保持，不许引入新依赖）**

- Next.js 16（App Router）+ React 19 + TypeScript
- **Tailwind CSS v4**：`app/globals.css` 里 `@import "tailwindcss"` + `@theme` 块把 CSS 变量映射成工具类
- **CSS 自定义属性驱动主题**：`--bg`、`--bg-panel`、`--bg-hover`、`--bg-selected`、`--border`、`--text`、`--text-muted`、`--text-dim`、`--accent`，以及排版变量 `--chat-content-max-width: 820px`、`--chat-content-font-size: 14px`
- **五套主题必须继续可用**：`light`（默认）、`dark`、`mist`、`pine`、`rose`。参考值：
  - light：`--bg #ffffff`、`--bg-panel #f5f5f5`、`--border #e0e0e0`、`--text #1a1a1a`、`--accent #245bce`
  - dark：`--bg #1a1a1a`、`--bg-panel #242424`、`--border #454545`、`--text #e8e8e8`、`--accent #a4c2f4`
- 局部 CSS Modules（如 `components/ChatMinimap.module.css`）
- Electron 桌面外壳，深色窗口背景 `#1a1a1a`

**实测到的审美问题（这是"为什么不够整齐"的硬证据，必须在提示词里被引用、被解决）**

1. **没有字号阶梯**：组件里出现 12 个不同字号——`9 / 10 / 11 / 12 / 12.5 / 13 / 14 / 15 / 16 / 18 / 20 / 22`，其中 10px(55 处)、11px(129 处)、12px(110 处)、13px(24 处) 四个相差 1px 的字号承担了绝大多数文本；`12.5px` 是明显的意外值。层级不是设计出来的，是长出来的。
2. **基础字号偏小**：正文主力落在 10–13px，信息密度靠"缩小字体"换取，读起来拥挤、不精致。
3. **颜色绕开 token**：组件里有 **182 处硬编码十六进制颜色**，而 `var(--…)` 用了 1132 处——约 14% 的颜色决策不跟随五套主题，换主题时会出现突兀色块。
4. **样式写在组件里**：`ChatWindow.tsx` 75 处、`SessionSidebar.tsx` 104 处、`ModelsConfig.tsx` 137 处内联 `style={{}}`，同一个视觉规则在多处重复且互相漂移。
5. **行宽未受控**：对话正文 `max-width: 820px` + 14px 正文，拉丁文一行超过 100 字符，长段落读起来累。

**不可破坏的东西（执行者的红线，必须写进提示词）**

- 行为、数据、接口、快捷键一律不变，只动视觉层
- 五套主题继续工作，所有颜色必须经由 CSS 变量
- 现有测试必须继续通过，特别是这些守卫文件：
  `lib/readme-branding.test.mjs`、`lib/desktop-packaging.test.mjs`、`lib/desktop-shell.test.mjs`、
  `lib/desktop-external-links.test.mjs`、`lib/webpi-extension.test.mjs`、`lib/port-selection.test.mjs`
- `npm run lint`、`node_modules/.bin/tsc --noEmit` 必须干净
- 不引入任何新的运行时依赖（不许装 UI 库、图标库、动画库）

## 你要产出的提示词必须包含的章节

1. **角色与边界**：执行者的身份、只能改视觉层、改完必须自己验证。
2. **现状诊断**：把上面第 1–5 条证据以清单形式引用（带数字），让执行者知道问题在哪。
3. **审美标准（可验证）**：把"更好看"翻译成数字。至少要覆盖：
   - **字号阶梯**：给出 5–6 级的完整阶梯（含每级的用途：界面小字 / 正文 / 小标题 / 标题 / 大标题 / 数字），相邻级差 ≥1.25 倍，正文 ≥14px，删除 12.5px 这类意外值
   - **行高与行宽**：正文行高 ≥1.5、标题 ≥1.2；单行拉丁字符数 65–75、中文 35–45（给出如何按 `max-width` 计算）
   - **间距节奏**：单一基数（如 4px）派生的 4–6 档间距，一屏内出现的不同间距值 ≤3
   - **颜色纪律**：100% 经 `var(--…)`；强调色占画面像素 ≤5%；语义色（成功/警告/错误）只在状态处出现
   - **对比度**：正文 ≥4.5:1、大字与 UI 边界 ≥3:1，**五套主题**逐一达标
   - **动效预算**：过渡 ≤200ms、只用一族缓动、尊重 `prefers-reduced-motion`
   - **对齐与网格**：同屏最多两种对齐线，禁止混用居中与左对齐的同类元素
4. **执行顺序**：分阶段并要求在阶段之间停下来给人看——① 先建 token 层（变量 + Tailwind `@theme` 映射）② 再改 1–2 个代表性组件做样板 ③ 确认后再铺开 ④ 全量验证。
5. **交付物契约**：改哪些文件、每个阶段必须给出什么证据（哪两个视口的截图、哪几条命令的输出、五套主题各一张对照图）。
6. **自检清单**：执行者改完后必须逐条回答，且答案必须是数字或命令输出，不能是形容词。
7. **反模式清单**：禁止"更现代/更精致"这类无判据表述、禁止紫蓝渐变糊墙、禁止毛玻璃堆叠、禁止改行为、禁止为了好看而删信息、禁止用假数据填充。

## 写作纪律（对你写出的提示词的要求）

- **每个形容词后面必须跟一个数**；跟不上的形容词删掉。
- 每条规则都要能被**读代码**或**量截图**验证；写不出验证方式的要求，不要写。
- 颜色只能引用项目已有的变量与上面给出的参考值，**不要发明新色值**。
- 中文输出；整体控制在 1200–1800 字，用二级标题分节，可直接整段粘贴使用。
- 若某条审美要求与"可验证"冲突，选可验证，并在提示词里写明取舍。
- 不要写"请你成为世界顶级设计师"这类空话；你的权威来自具体判据。

## 输出格式

先给一段**不超过 5 行的思路说明**：你认为最关键的 3 条规则是什么、为什么它们能解决上面第 1–5 条问题。

然后给出**一个完整提示词**，放进代码块，标题为「交给编码 agent 的提示词」，可直接复制执行。

最后给一张**自检表**（Markdown 表格，3 列：你写的规则 / 执行者如何验证 / 命中了哪条现状问题），列 6–8 行。

## 交付前的自我审查（你必须先做一遍）

1. 你写的提示词里，是否每条审美规则都有数字或命令？
2. 是否有可能被"看起来很现代"的套话钻空子？
3. 是否明确禁止了新依赖、明确了五套主题与六个守卫测试必须通过？
4. 执行者能否在**不问你**的情况下判断自己是否达标？
5. 如果有人只照做前两条规则，画面会明显变好吗？

任何一条答"否"，改完再输出。
